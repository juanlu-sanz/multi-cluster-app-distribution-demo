= Step 2 - Submariner: Cross-Cloud Cluster Connectivity
include::_attributes.adoc[]

This step deploys Submariner via ACM to establish encrypted L3 connectivity between Cluster A (AWS) and Cluster B (Azure). Submariner creates an IPsec tunnel between the clusters, enabling pods and services to communicate across cloud providers without exposing anything to the public internet. This provides the network foundation that xref:04-service-mesh.adoc[Step 3 (Service Mesh)] builds on for cross-cluster traffic management.

== Prerequisites

* ACM Hub cluster with workload placement from xref:02-acm-workload-placement.adoc[Step 1] fully operational
* Both managed clusters (`cluster-a` and `cluster-b`) joined to the Hub and members of the `production-clusters` ManagedClusterSet
* `oc` CLI authenticated as cluster-admin on the Hub cluster
* Contexts renamed as described in the xref:00-setup.adoc[Cluster Setup] section
* Cloud provider credentials available for both managed clusters (see below)

=== Cloud provider credentials

Submariner needs cloud credentials to configure gateway nodes and open the required firewall rules (NSGs on Azure, security groups on AWS). If ACM provisioned your clusters, these credentials already exist. If the clusters were imported manually, create them before proceeding.

*Verify credentials exist:*

[.console-input]
[source,bash]
----
oc get secret cluster-a-cloud-creds -n cluster-a --context hub
oc get secret cluster-b-cloud-creds -n cluster-b --context hub
----

If either secret is missing, create it:

*Cluster A (AWS):*

[.console-input]
[source,bash]
----
oc create secret generic cluster-a-cloud-creds -n cluster-a --context hub \
  --from-literal=aws_access_key_id="<AWS_ACCESS_KEY_ID>" \
  --from-literal=aws_secret_access_key="<AWS_SECRET_ACCESS_KEY>"
----

*Cluster B (Azure):*

[.console-input]
[source,bash]
----
oc create secret generic cluster-b-cloud-creds -n cluster-b --context hub \
  --from-literal=osServicePrincipal.json='{
    "clientId": "<AZURE_CLIENT_ID>",
    "clientSecret": "<AZURE_CLIENT_SECRET>",
    "tenantId": "<AZURE_TENANT_ID>",
    "subscriptionId": "<AZURE_SUBSCRIPTION_ID>"
  }'
----

NOTE: These credentials need permission to modify security group rules (AWS) and NSG rules (Azure). The minimum required permissions are documented in the link:https://docs.redhat.com/en/documentation/red_hat_advanced_cluster_management_for_kubernetes/2.11/html/add-ons/submariner#preparing-selected-hosts-to-deploy-submariner[Submariner cloud preparation guide].

== Steps to Apply

[#broker-namespace]
=== 1. Create the Submariner broker namespace

*What:* Create the namespace where the Submariner Broker will run on the Hub.

*Why:* The Broker is the rendezvous point where managed clusters exchange endpoint information. ACM expects the broker namespace to follow the `<managedclusterset-name>-broker` naming convention.

[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc apply -f 02-submariner-connectivity/broker-namespace.yaml --context hub
----

.Verify: Broker namespace created
[%collapsible]
====
[.console-input]
[source,bash]
----
oc get namespace production-clusters-broker --context hub
----

[.console-output]
[source,bash]
----
NAME                          STATUS   AGE
production-clusters-broker    Active   10s
----
====

'''

[#deploy-broker]
=== 2. Deploy the Submariner Broker

*What:* Create the Broker CR that coordinates cross-cluster discovery and tunnel establishment.

*Why:* The Broker stores the endpoint information that each managed cluster's gateway needs to find and connect to its peers. Without the Broker, the clusters have no way to discover each other.

[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc apply -f 02-submariner-connectivity/broker.yaml --context hub
----

.Verify: Broker deployed
[%collapsible]
====
[.console-input]
[source,bash]
----
oc get broker submariner-broker -n production-clusters-broker --context hub
----

[.console-output]
[source,bash]
----
NAME                AGE
submariner-broker   10s
----
====

'''

[#submariner-config]
=== 3. Create the SubmarinerConfig for each managed cluster

*What:* Create SubmarinerConfig CRs that tell ACM how to prepare each managed cluster for Submariner - including which credentials to use and how many gateway nodes to designate.

*Why:* Each cloud provider needs different preparation. On AWS, Submariner opens security group rules for IPsec traffic (UDP 4500, UDP 500). On Azure, it opens NSG rules for the same ports. The SubmarinerConfig also designates worker nodes as gateway nodes, which handle the encrypted tunnel endpoints.

[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc apply -f 02-submariner-connectivity/submariner-config-cluster-a.yaml --context hub
oc apply -f 02-submariner-connectivity/submariner-config-cluster-b.yaml --context hub
----

.Verify: SubmarinerConfig created for both clusters
[%collapsible]
====
[.console-input]
[source,bash]
----
oc get submarinerconfig submariner -n cluster-a --context hub
oc get submarinerconfig submariner -n cluster-b --context hub
----

[.console-output]
[source,bash]
----
NAME          AGE
submariner    10s
----
====

'''

[#deploy-addon]
=== 4. Deploy the Submariner add-on on each managed cluster

*What:* Create ManagedClusterAddOn resources to trigger the Submariner installation on both managed clusters.

*Why:* ACM manages Submariner as an add-on. Creating this resource tells ACM to install the Submariner operator, gateway engine, and route agent on the target cluster. The gateway engine establishes the IPsec tunnel to the peer cluster, and the route agent configures the host networking so pod and service CIDRs are routable across the tunnel.

[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc apply -f 02-submariner-connectivity/addon-cluster-a.yaml --context hub
oc apply -f 02-submariner-connectivity/addon-cluster-b.yaml --context hub
----

[#webhook-workaround]
==== Workaround: Remove the broker-validator webhook

On ACM 2.17.x there is a known issue where the `submariner-addon-broker-validator` webhook incorrectly resolves the cluster identity from the service account name (e.g. it resolves `cluster-a` as `a`). This blocks both gateway endpoint registration in the broker namespace _and_ Lighthouse ServiceImport propagation across clusters (causing `.svc.clusterset.local` DNS resolution to fail). Delete the webhook after deploying the add-ons:

[.console-input]
[source,bash]
----
oc delete validatingwebhookconfiguration submariner-addon-broker-validator --context hub --ignore-not-found
----

NOTE: The ACM operator may recreate this webhook during reconciliation. If the gateway connections do not establish after several minutes, check if the webhook has been recreated and delete it again.

.Verify: Submariner add-on installed and connected
[%collapsible]
====
Wait 2-3 minutes for the add-on to install and the gateways to establish the tunnel.

Check add-on status:

[.console-input]
[source,bash]
----
oc get managedclusteraddon submariner -n cluster-a --context hub
oc get managedclusteraddon submariner -n cluster-b --context hub
----

[.console-output]
[source,bash]
----
NAME          AVAILABLE   DEGRADED   STATUS
submariner    True        False
----

Check the gateway connection on each cluster:

[.console-input]
[source,bash]
----
oc get gateways.submariner.io -n submariner-operator --context cluster-a
----

[.console-output]
[source,bash]
----
NAME           HA STATUS
<gateway-node> active
----

[.console-input]
[source,bash]
----
oc get gateways.submariner.io -n submariner-operator --context cluster-b
----

[.console-output]
[source,bash]
----
NAME           HA STATUS
<gateway-node> active
----

Verify the connection is established:

[.console-input]
[source,bash]
----
oc get gateways.submariner.io -n submariner-operator --context cluster-a \
  -o jsonpath='{range .items[*].status.connections[*]}Status: {.status} | RTT: {.latencyRTT.average}{"\n"}{end}'
----

The output should show `Status: connected` with a valid RTT, confirming the IPsec tunnel is established between AWS and Azure.
====

'''

[#deploy-cluster-b]
=== 5. Deploy the demo-app to Cluster B

*What:* Deploy the demo-app to Cluster B so both clusters have a running instance of the service.

*Why:* After xref:02-acm-workload-placement.adoc[Step 1], the ApplicationSet deploys the demo-app only to Cluster A. The connectivity test in the next step needs a running service on Cluster B to reach through the Submariner tunnel. Step 3 (Service Mesh) also requires the app on both clusters for cross-cluster traffic routing.

[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc apply -f 00-current-state/namespace.yaml --context cluster-b
oc apply -f 00-current-state/deployment.yaml --context cluster-b
oc apply -f 00-current-state/service.yaml --context cluster-b
----

NOTE: We intentionally skip the Route on Cluster B - traffic will be routed through the Submariner tunnel and later through the Service Mesh, not via public ingress.

.Verify: Application running on Cluster B
[%collapsible]
====
[.console-input]
[source,bash]
----
oc get pods -n demo-app --context cluster-b
----

[.console-output]
[source,bash]
----
NAME                        READY   STATUS    RESTARTS   AGE
demo-app-6d4f5b7c8-a3b4n   1/1     Running   0          25s
demo-app-6d4f5b7c8-k7m9p   1/1     Running   0          25s
----
====

'''

[#service-export]
=== 6. Create ServiceExports for cross-cluster DNS

*What:* Create `ServiceExport` resources on both clusters to register the demo-app service with Submariner's Lighthouse DNS.

*Why:* Submariner's Lighthouse DNS resolves `.svc.clusterset.local` domain names, but only for services that have been explicitly exported with a `ServiceExport`. Without this, the connectivity test will fail with "Could not resolve host" even though the tunnel is connected.

[.console-input]
[source,bash,subs="+macros,+attributes"]
----
cat <<'EOF' | oc apply --context cluster-a -f -
apiVersion: multicluster.x-k8s.io/v1alpha1
kind: ServiceExport
metadata:
  name: demo-app
  namespace: demo-app
EOF

cat <<'EOF' | oc apply --context cluster-b -f -
apiVersion: multicluster.x-k8s.io/v1alpha1
kind: ServiceExport
metadata:
  name: demo-app
  namespace: demo-app
EOF
----

.Verify: ServiceExport and ServiceImport created
[%collapsible]
====
Wait 30-60 seconds for Lighthouse to propagate the ServiceImport across clusters.

[.console-input]
[source,bash]
----
oc get serviceexport -n demo-app --context cluster-a
oc get serviceexport -n demo-app --context cluster-b
----

[.console-input]
[source,bash]
----
oc get serviceimport -n demo-app --context cluster-a
oc get serviceimport -n demo-app --context cluster-b
----

Both clusters should show a `ServiceImport` with type `ClusterSetIP`.

NOTE: If the ServiceImport does not appear after 60 seconds, check whether the `submariner-addon-broker-validator` webhook has been recreated (see <<webhook-workaround>>). This webhook also blocks Lighthouse ServiceImport propagation, not just gateway registration.
====

'''

[#verify-connectivity]
=== 7. Verify cross-cluster connectivity

*What:* Run a connectivity test from a pod on one cluster to a service on the other cluster, proving the Submariner tunnel works.

*Why:* Before proceeding to Step 3 (Service Mesh), we need to confirm that the L3 tunnel is operational and that pods on Cluster A (AWS) can reach pods on Cluster B (Azure) and vice versa. This is the foundation that all cross-cluster traffic management depends on.

Deploy a test pod on Cluster A and try to reach a service on Cluster B:

[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc run submariner-test --image=registry.access.redhat.com/ubi9/ubi-minimal:latest \
  -n demo-app --context cluster-a --restart=Never --rm -i \
  --overrides='{
    "spec": {
      "securityContext": {"runAsNonRoot": true, "seccompProfile": {"type": "RuntimeDefault"}},
      "containers": [{
        "name": "submariner-test",
        "image": "registry.access.redhat.com/ubi9/ubi-minimal:latest",
        "command": ["curl", "-s", "--max-time", "10", "http://demo-app.demo-app.svc.clusterset.local:9090"],
        "securityContext": {"allowPrivilegeEscalation": false, "capabilities": {"drop": ["ALL"]}}
      }]
    }
  }'
----

[.console-output]
[source,json]
----
{"name":"demo-app","uri":"/","type":"HTTP","body":"Hello from demo-app","code":200}
----

NOTE: The `.svc.clusterset.local` domain is provided by Submariner's Lighthouse DNS. It resolves to the remote cluster's service, proving end-to-end cross-cloud connectivity.

If the demo-app is not yet deployed on Cluster B, you can verify basic connectivity using the Submariner diagnostic tool:

[.console-input]
[source,bash]
----
subctl diagnose all --context cluster-a
----

.Verify: Submariner status summary
[%collapsible]
====
[.console-input]
[source,bash]
----
subctl show all --context cluster-a
----

[.console-output]
[source,bash]
----
CLUSTER ID                    ENDPOINT IP     PUBLIC IP       CABLE DRIVER   TYPE
cluster-a                     10.1.x.x        <aws-ip>        libreswan      local
cluster-b                     10.0.x.x        <azure-ip>       libreswan      remote

GATEWAY                       CLUSTER         REMOTE IP       NAT   CABLE DRIVER   SUBNETS                    STATUS   RTT avg
cluster-b-gateway-0           cluster-b       <azure-ip>       yes   libreswan      10.128.0.0/14, ...        connected   5.2ms
----

The `connected` status and RTT measurement confirm the tunnel is active between AWS and Azure.
====

'''

[#export-remote-ip]
=== 8. Export the remote ingress IP for Service Mesh

*What:* Capture the ClusterIP of the demo-app service on the remote cluster and export it as `REMOTE_INGRESS_IP`.

*Why:* xref:04-service-mesh.adoc[Step 3 (Service Mesh)] uses this IP in the ServiceEntry to route traffic to the remote cluster. Now that Submariner is active, internal ClusterIPs are reachable across clusters through the IPsec tunnel.

[.console-input]
[source,bash,subs="+macros,+attributes"]
----
export REMOTE_INGRESS_IP=$(oc get svc demo-app -n demo-app --context cluster-b -o jsonpath='{.spec.clusterIP}')
echo "REMOTE_INGRESS_IP=$REMOTE_INGRESS_IP"
----

.Verify: variable is set
[%collapsible]
====
[.console-input]
[source,bash]
----
echo $REMOTE_INGRESS_IP
----

The output should be a valid ClusterIP address (e.g. `172.30.x.x`).
====

NOTE: If the demo-app is not yet deployed on cluster-b, this export will be empty. You can set it later before Step 3, but the value must be exported before running `envsubst` on the ServiceEntry manifest.

'''

== What This Solves

[cols="2,3",options="header"]
|===
| Problem | How Submariner Solves It

| No network path between clouds
| IPsec tunnel connects AWS VPC and Azure VNet at the pod/service CIDR level

| Public IP exposure for cross-cluster traffic
| All inter-cluster traffic flows through the encrypted tunnel - no public service endpoints needed

| Manual VPN/peering configuration
| ACM deploys and manages Submariner as an add-on - no cloud-specific VPN setup required

| Cloud firewall complexity
| Submariner automatically opens the required security group rules (AWS) and NSG rules (Azure)

| Multi-cluster service discovery
| Lighthouse DNS provides `.svc.clusterset.local` names for services across clusters
|===

[cols="2,3",options="header"]
|===
| Remaining Problem | Addressed In

| Application-level traffic routing (canary, blue-green)
| xref:04-service-mesh.adoc[Step 3 - Service Mesh]

| Zero-trust mTLS between services

| Weighted traffic splitting across clusters
| xref:04-service-mesh.adoc[Step 3 - Service Mesh]
|===

== Alternatives Considered

[cols="2,4",options="header"]
|===
| Approach | Notes

| Submariner via ACM (this solution)
| Managed as an ACM add-on, automatic cloud preparation, encrypted tunnels, integrated service discovery. Requires ACM.

| Site-to-site VPN (Azure VPN Gateway + AWS VPN Gateway)
| Cloud-native but requires manual setup on both sides, ongoing management, and does not provide service-level discovery.

| Public ingress IPs
| Simplest approach - expose services publicly and reference the public IPs. Works for demos but not acceptable for production (security, cost, latency).

| VPC/VNet peering via cloud APIs
| Requires same-provider or specific peering support. Does not work natively across Azure and AWS.

| Skupper (Service Interconnect)
| Application-layer connectivity (L7). Good for specific service-to-service links but does not provide the full L3 connectivity that Service Mesh needs for multi-cluster routing.
|===

== Reset

To undo everything from this step and return to the state before Submariner was deployed, run the following commands. This removes the add-ons (which uninstalls Submariner from both managed clusters), the SubmarinerConfigs, the Broker, and the broker namespace. Cloud credential secrets are intentionally preserved so they can be reused on the next run.

[.console-input]
[source,bash]
----
oc delete managedclusteraddon submariner -n cluster-a --context hub --ignore-not-found
oc delete managedclusteraddon submariner -n cluster-b --context hub --ignore-not-found
oc wait --for=delete managedclusteraddon/submariner -n cluster-a --context hub --timeout=300s 2>/dev/null || true
oc wait --for=delete managedclusteraddon/submariner -n cluster-b --context hub --timeout=300s 2>/dev/null || true
oc delete submarinerconfig submariner -n cluster-a --context hub --ignore-not-found
oc delete submarinerconfig submariner -n cluster-b --context hub --ignore-not-found
oc delete broker submariner-broker -n production-clusters-broker --context hub --ignore-not-found
oc delete namespace production-clusters-broker --context hub --ignore-not-found
----

NOTE: After deleting the ManagedClusterAddOns, ACM will uninstall the Submariner operator and all its components (gateway, route agent, Lighthouse) from the managed clusters. The `submariner-operator` namespace on each managed cluster will be removed automatically. This process may take 2-3 minutes.

NOTE: The ACM operator will recreate the `submariner-addon-broker-validator` webhook after reconciliation. When re-running this step, remember to delete it again as described in the <<webhook-workaround>> section.
