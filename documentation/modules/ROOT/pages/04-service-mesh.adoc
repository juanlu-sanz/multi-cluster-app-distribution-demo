= Step 3 - Solution: Service Mesh for Traffic Management
include::_attributes.adoc[]

This step adds OpenShift Service Mesh {mesh-version} (Istio ambient mode) on top of the ACM placement from xref:02-acm-workload-placement.adoc[Step 1] and the Submariner connectivity from xref:03-submariner-connectivity.adoc[Step 2]. With Service Mesh, traffic routing is decoupled from the underlying cluster and cloud provider - consumers hit a stable service endpoint, and the mesh transparently routes traffic to whichever cluster is currently running the workload, whether it's on Azure or AWS. This enables zero-downtime migrations, blue-green failover, canary traffic shifting, and zero-trust mutual TLS between services - all without changing DNS records or load balancers.

== Prerequisites

* ACM Hub cluster with workload placement from xref:02-acm-workload-placement.adoc[Step 1] fully operational
* Submariner cross-cloud connectivity from xref:03-submariner-connectivity.adoc[Step 2] verified and working
* At least two managed clusters (`cluster-a` on AWS, `cluster-b` on Azure) joined to the Hub
* OpenShift Service Mesh {mesh-version} Operator installed on all participating clusters (Hub + managed)
* `oc` CLI authenticated as cluster-admin on the Hub cluster
* Contexts renamed as described in the xref:00-setup.adoc[Cluster Setup] section

NOTE: Cross-cluster network connectivity is provided by Submariner (Step 2). The `$REMOTE_INGRESS_IP` used in the ServiceEntry can be an internal cluster IP because Submariner's IPsec tunnel makes it reachable across Azure and AWS.

NOTE: Service Mesh resources are applied directly on the managed clusters. Every `oc` command specifies `--context cluster-a` or `--context cluster-b` explicitly.

== Steps to Apply

[#deploy-both-clusters]
=== 1. Deploy the application to both clusters

*What:* Update the Placement from Step 1 to select both managed clusters, so the application runs on cluster-a and cluster-b simultaneously.

*Why:* Cross-cluster traffic management (canary, blue-green, weighted routing) requires the application to be running on both clusters. In Step 1, the Placement selected only one cluster at a time. For Service Mesh to route traffic between clusters, both must have the workload deployed. Removing the `numberOfClusters: 1` constraint and broadening the label selector allows the ApplicationSet to generate Applications for both clusters.

[.console-input]
[source,bash,subs="+macros,+attributes"]

oc patch placement demo-app-placement -n openshift-gitops --context hub --type merge \
  -p '{"spec":{"numberOfClusters": 2, "predicates":[{"requiredClusterSelector":{"labelSelector":{"matchLabels":{"environment":"production"}}}}]}}'
----

.Verify: Application running on both clusters
[%collapsible]

Wait 30-60 seconds for Argo CD to sync.

[.console-input]

demo-app-cluster-b   Synced   Healthy   ...
----

[.console-input]
[source,bash]

oc get pods -n demo-app --context cluster-a

Both clusters should show running pods.
====

.Verify: Application accessible in the browser
[%collapsible]

[#install-istio]
=== 2. Install the Istio control plane in ambient mode

*What:* Deploy the Istio control plane using the ambient profile, which installs a ztunnel DaemonSet on every node for Layer 4 traffic interception.

*Why:* Ambient mode replaces the traditional sidecar model (one envoy container per pod) with a per-node proxy. This reduces resource overhead and simplifies adoption - existing workloads join the mesh without restarting or injecting sidecars. The ztunnel handles mTLS and Layer 4 routing transparently.

First, create the required namespaces on both clusters:

[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc create namespace istio-system --context cluster-a
oc create namespace istio-system --context cluster-b
oc create namespace istio-cni --context cluster-a
oc create namespace istio-cni --context cluster-b
----

Deploy the Istio CNI plugin (required for ambient mode to intercept traffic at the kernel level):

[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc apply -f 03-service-mesh-traffic-management/istio-cni.yaml --context cluster-a
oc apply -f 03-service-mesh-traffic-management/istio-cni.yaml --context cluster-b
----

Wait ~30 seconds for the CNI DaemonSet to become ready, then deploy the Istio control plane and the ztunnel DaemonSet:

[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc apply -f 03-service-mesh-traffic-management/istio.yaml --context cluster-a
oc apply -f 03-service-mesh-traffic-management/istio.yaml --context cluster-b
oc apply -f 03-service-mesh-traffic-management/ztunnel.yaml --context cluster-a
oc apply -f 03-service-mesh-traffic-management/ztunnel.yaml --context cluster-b
----

.Verify: Istio control plane running
[%collapsible]
====
Wait 60-90 seconds for all components to reconcile.

[.console-input]
[source,bash]
----
oc get istio default -n istio-system --context cluster-a
----

[.console-output]
[source,bash]
----
NAME      NAMESPACE      PROFILE   REVISIONS   READY   IN USE   ACTIVE REVISION   STATUS    VERSION   AGE
default   istio-system   ambient   1           1       0        default           Healthy   v1.30.1   90s
----

[.console-input]
[source,bash]
----
oc get daemonset ztunnel -n istio-system --context cluster-a
----

[.console-output]
[source,bash]
----
NAME      DESIRED   CURRENT   READY   UP-TO-DATE   AVAILABLE   AGE
ztunnel   2         2         2       2            2           60s
----

NOTE: If the ztunnel pods show `0/1 Ready` with errors about `/var/run/ztunnel/ztunnel.sock` not found, restart them with `oc delete pods -n istio-system -l app=ztunnel --context cluster-a`. This can happen if the ztunnel pods started before the CNI agent was ready.
====

[IMPORTANT]
====
The `istio.yaml` manifest includes `CA_TRUSTED_NODE_ACCOUNTS: "istio-system/ztunnel,kube-system/ztunnel"` in the pilot environment variables. This setting tells istiod which service accounts are trusted to request certificates on behalf of workload identities (required for ambient mode). The sail operator may default to `kube-system/ztunnel`, but when the ztunnel DaemonSet runs in `istio-system` (as in this demo), that default is incorrect. Without this fix, ztunnel cannot obtain SPIFFE certificates for workload pods, causing all inbound connections (including health probes) to time out with `context deadline exceeded`.

If you see `impersonation failed for identity` errors in the istiod logs, verify this setting:

[.console-input]
[source,bash]
----
oc get deployment istiod -n istio-system --context cluster-a -o yaml | grep CA_TRUSTED_NODE_ACCOUNTS
----

The output must include `istio-system/ztunnel`.
====

[#enroll-namespace]
=== 4. Enroll the application namespace into the mesh

*What:* Label the `demo-app` namespace with `istio.io/dataplane-mode=ambient` on both managed clusters.

*Why:* In ambient mode, the mesh is opt-in at the namespace level. Adding this label tells the ztunnel DaemonSet to intercept traffic for all pods in this namespace - enabling mTLS encryption and Layer 4 policy enforcement without any changes to the application itself.

[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc label namespace demo-app istio.io/dataplane-mode=ambient --context cluster-a --overwrite
oc label namespace demo-app istio.io/dataplane-mode=ambient --context cluster-b --overwrite
----

NOTE: The deployment manifests in this repository already use **exec-based probes** (`wget --spider -q http://localhost:9090/...`) instead of HTTP probes. This is intentional — in ambient mode, the ztunnel intercepts _all_ inbound traffic to the pod, including the kubelet's HTTP health check connections from the host network. HTTP probes time out because they are routed through the ztunnel proxy layer. Exec probes run inside the container and hit `localhost`, bypassing ztunnel entirely. If you are adapting this demo with your own workloads that use HTTP probes, you will need to switch them to exec probes before enrolling the namespace into the mesh — otherwise the pods will enter `CrashLoopBackOff`.

After labeling the namespace, restart the pods so they come up fresh inside the mesh:

[.console-input]
[source,bash]
----
oc rollout restart deployment demo-app -n demo-app --context cluster-a
oc rollout restart deployment demo-app -n demo-app --context cluster-b
----

.Verify: Namespace enrolled in the mesh
[%collapsible]
====
[.console-input]
[source,bash]
----
oc get namespace demo-app --show-labels --context cluster-a | grep istio
----

[.console-output]
[source,bash]
----
istio.io/dataplane-mode=ambient
----
====

[#virtual-service]

*Why:* The VirtualService is the traffic control layer. This is what eliminates DNS changes on migration: the endpoint stays the same, only the routing weights change.

[#mtls]
=== 11. Apply the PeerAuthentication for zero-trust mTLS

*What:* Enforce STRICT mutual TLS for the `demo-app` namespace on both clusters, requiring all communication to present a valid mesh identity.

*Why:* This implements zero-trust networking at the pod level. No application can communicate with `demo-app` unless it is part of the mesh and has a valid SPIFFE identity. This replaces namespace-level network policies with identity-based authentication - a more granular security model that works consistently across clusters.

[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc apply -f 03-service-mesh-traffic-management/peer-authentication.yaml --context cluster-a
oc apply -f 03-service-mesh-traffic-management/peer-authentication.yaml --context cluster-b
----

[WARNING]
====
**STRICT mTLS and OpenShift Routes:** Enforcing `STRICT` mode means the ztunnel will reject _all_ non-mTLS inbound traffic — including connections from the OpenShift HAProxy router (which runs in the `openshift-ingress` namespace, outside the mesh). If you have an OpenShift `Route` pointing to the `demo-app` service, it will stop working after applying PeerAuthentication with `STRICT` mode (the route will return _"Application is not available"_).

**Workaround options:**

1. **Use the route for demo purposes only before applying PeerAuth.** Show the route verification in earlier steps, then apply PeerAuth as the final zero-trust hardening step (accepting that external route access is now blocked in favor of mesh-only communication).
2. **Use an Istio ingress gateway** instead of OpenShift Routes — the gateway participates in the mesh and has a valid SPIFFE identity.
3. **Use `PERMISSIVE` mode** instead of `STRICT` if you need to allow both mTLS and plaintext traffic during a transition period.
====

.Verify: mTLS enforced
[%collapsible]
====
[.console-input]
[source,bash]
----
oc get peerauthentication -n demo-app --context cluster-a
----

[.console-output]
[source,bash]
----
NAME               MODE     AGE
demo-app-strict    STRICT   10s
----

To confirm mTLS is active, attempt a request from a pod that is not part of the mesh:

[.console-input]
[source,bash]
----
oc run test-pod --image=registry.access.redhat.com/ubi9/ubi-minimal:latest \
  -n default --context cluster-a --restart=Never --rm -i -- \
  curl -s http://demo-app.demo-app.svc.cluster.local:9090
----

[.console-output]
[source,bash]
----
curl: (56) Recv failure: Connection reset by peer
----
====

== What This Solves (Combined with Steps 1 and 2)

[cols="2,3",options="header"]
|===
| Problem from Step 0 | How ACM + Submariner + Service Mesh Solve It

| DNS/Route changes on every migration
| Service Mesh provides a stable virtual endpoint - consumers never see the cluster or cloud switch

| No traffic shifting
| VirtualService enables canary, blue-green, and weighted traffic splits across Azure and AWS

| All-or-nothing migration
| Gradual traffic shifting allows validation before committing to the new cloud/cluster

| No zero-trust networking
| PeerAuthentication enforces strict mTLS - services communicate only with explicitly allowed peers, even across clouds

| External LB reconfiguration
| Service Mesh handles routing internally over the Submariner tunnel - no cloud-specific LB changes needed for workload moves
|===

== Alternatives Considered

[cols="2,4",options="header"]
|===
| Approach | Notes

| Service Mesh (this solution)
| Full L4/L7 traffic management, mTLS, canary, blue-green - all declarative. Requires mesh installation on all clusters.

| F5 Global Traffic Manager (GTM)
| External LB can route traffic between clusters, but requires manual or API-driven configuration changes. Not part of the Red Hat stack.

| Azure Traffic Manager / Front Door
| Cloud-native option for Azure workloads. Adds latency for health probes and limits L7 capabilities compared to Service Mesh.

| DNS-based failover (Route53 / external DNS)
| Simple but slow (DNS TTL propagation) and lacks fine-grained traffic control (no canary, no weighted splits).
|===

== Reset

To remove all resources created in this step and return to the state before Service Mesh was configured:

[.console-input]
[source,bash]
----
# Remove mesh resources from both clusters
oc delete peerauthentication demo-app-strict -n demo-app --context cluster-a --ignore-not-found
oc delete peerauthentication demo-app-strict -n demo-app --context cluster-b --ignore-not-found
oc delete virtualservice demo-app-routing -n demo-app --context cluster-a --ignore-not-found
oc delete destinationrule demo-app-dr -n demo-app --context cluster-a --ignore-not-found
oc delete serviceentry demo-app-cross-cluster -n demo-app --context cluster-a --ignore-not-found
oc delete serviceentry demo-app-cross-cluster -n demo-app --context cluster-b --ignore-not-found
oc delete gateway demo-app-waypoint -n demo-app --context cluster-a --ignore-not-found
oc delete gateway demo-app-waypoint -n demo-app --context cluster-b --ignore-not-found

# Remove ambient label from namespace
oc label namespace demo-app istio.io/dataplane-mode- --context cluster-a
oc label namespace demo-app istio.io/dataplane-mode- --context cluster-b

# Remove Kiali and OSSMC
oc delete ossmconsole ossmconsole -n openshift-operators --context cluster-a --ignore-not-found
oc delete ossmconsole ossmconsole -n openshift-operators --context cluster-b --ignore-not-found
oc delete kiali kiali -n istio-system --context cluster-a --ignore-not-found
oc delete kiali kiali -n istio-system --context cluster-b --ignore-not-found
oc delete clusterrolebinding kiali-monitoring-rbac --context cluster-a --ignore-not-found
oc delete clusterrolebinding kiali-monitoring-rbac --context cluster-b --ignore-not-found

# Remove Istio control plane, ztunnel, and CNI
oc delete ztunnel default -n istio-system --context cluster-a --ignore-not-found
oc delete ztunnel default -n istio-system --context cluster-b --ignore-not-found
oc delete istio default -n istio-system --context cluster-a --ignore-not-found
oc delete istio default -n istio-system --context cluster-b --ignore-not-found
oc delete istiocni default --context cluster-a --ignore-not-found
oc delete istiocni default --context cluster-b --ignore-not-found
oc delete namespace istio-system --context cluster-a --ignore-not-found
oc delete namespace istio-system --context cluster-b --ignore-not-found
oc delete namespace istio-cni --context cluster-a --ignore-not-found
oc delete namespace istio-cni --context cluster-b --ignore-not-found

# Revert Placement to single cluster (Step 1 original state)
oc patch placement demo-app-placement -n openshift-gitops --context hub --type merge \
  -p '{"spec":{"numberOfClusters": 1, "predicates":[{"requiredClusterSelector":{"labelSelector":{"matchLabels":{"region":"west-europe"}}}}]}}'
----
